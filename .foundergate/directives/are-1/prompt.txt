PHASE 1 — ARCHITECTURAL PLACEMENT

Do not build an independent omnipotent autonomous agent.

Place the mechanism across existing FounderGate responsibilities:

- MOD-001 Core:
  loads the active run envelope and refuses unmanaged execution;

- MOD-004 Product Intake Officer:
  validates the software blueprint;

- MOD-005 CTO Planner:
  compiles accepted blueprint requirements into Spec Cards and lane plans;

- MOD-013 Branch/PR/Lane Orchestrator:
  binds lanes and repository work to blueprint requirements;

- MOD-014 Gate/Witness Engine:
  classifies and emits only true founder gates;

- MOD-015 Audit Log / Proof Ledger:
  records append-only run events and final proof capsules;

- MOD-018 Integration Merge Gate:
  records mechanically authorized lifecycle transitions;

- MOD-022 GitHub Connector:
  executes bounded repository actions but does not decide authority;

- SCL:
  executes approved sandbox Check Plans;

- ARLC:
  performs qualified repository lifecycle work;

- Terminal-0:
  remains the sole integration and sequential write sheriff.

No component may:

- define the blueprint;
- grant authority;
- execute the work;
- check its own result;
- and certify completion.

Maintain separation of duties.

PHASE 10 — PATTERN PROMOTION LAW

Do not automatically convert one successful run into permanent product behavior.

A run pattern becomes PROMOTION_ELIGIBLE only when:

- exact behavior is named;
- blueprint and manifest are available;
- evidence is complete;
- checker is clean;
- no hidden founder operation was required;
- result is reproducible;
- negative cases pass;
- safety boundaries are explicit;
- rollback is proven;
- at least two independent successful executions exist, unless the active policy permits one for low-risk deterministic behavior.

Pattern states:

CANDIDATE

CHECKER_CLEAN
PROMOTION_ELIGIBLE

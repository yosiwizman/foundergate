## 1. Purpose

To record, in one place, the founder's clarified operating direction on four points:

1. Technical proof proceeds before market validation.
2. Market validation is not a blocker for technical beta completion.
3. Paid-customer proof is a later, founder-controlled commercial gate.
4. A founder-controlled second account may supply valid cross-account **technical** evidence — and may never be labelled as outside-customer validation.

The founder's framing: before selling a car, you prove the car drives, brakes, changes gears, survives controlled tests, and produces safety evidence. Market demand is tested afterwards. FounderGate proves the car works first — for the founder, on public repos, across accounts, through repeated controlled runs.

**Out of scope.** Any change to existing requirements, controls, gates, evidence classes, conflicts, clarifications, limitations, or source attributions in the master Constitution. This amendment adds no product requirement and removes none.

## 3. Founder Clarification

The founder rejects treating outside-user validation, real prospects, willingness-to-pay, or paid customers as blockers for the current technical proof phase.

The founder holds a separate GitHub / AKIOR account usable for separate project repositories. Work executed against that account produces evidence from disk, Git, exact commits, repository state, tests, and sealed evidence packages. The identity of the account owner does not weaken that technical evidence.

The founder further directs that such work must never be presented as outside-customer validation, independent market validation, paid-customer proof, or third-party design-partner proof.

## 4. Definitions

| Term | Meaning |
| --- | --- |
| **Technical proof** | Evidence that a defined workflow executed as described, bound to exact commits and disk state, with tests, reports, and sealed evidence packages. |
| **Founder technical proof** | Technical proof produced on the founder's own primary project, operated by or for the founder. |
| **Self-owned demo proof** | Technical proof on a demonstration target the founder owns, used to exercise repo and objective flow under control. |
| **Cross-account technical proof** | Technical proof on a repository under a *different* founder-controlled account, including AKIOR. Proves portability across account boundaries. Proves nothing about customers. |
| **Outside-person validation** | A person who is not the founder, and not acting for the founder, using the product and reporting on it. Does not exist today. |
| **Market validation** | Evidence that people outside the founder's control want the product enough to adopt it. Does not exist today. |
| **Paid-customer proof** | A real payment, honestly recorded, for the product. May come from a friend, a small group, or a narrow market and still count — provided it is recorded as what it is. Does not exist today. |
| **Commercial pilot** | A founder-selected friend, prospect, or buyer using the product under founder-controlled conditions. |
| **SaaS platform readiness** | Proven hosted mechanics: auth, deployment, billing, support, repo access, data boundaries, security posture, operating controls. Not proven. |
| **True founder gate** | A decision the machine may not take: the next action is irreversible, live, spend-bearing, privacy-sensitive, or gate-changing. |
| **Proven with limits** | Proven for the exact scope tested, under the recorded conditions, and no further. The limits travel with the claim. |

## 6. Cross-Account Evidence Rule

A repository under AKIOR or any other founder-controlled account **may** be used as valid technical evidence when the result is supported by exact commit identifiers, disk and Git evidence, test results, checker and advisor reports, and sealed evidence packages.

**What cross-account proof establishes.** That the workflow operates across an account boundary, on a repository outside the primary one, producing the same evidence discipline.

**What it does not establish.** Outside-customer validation. Independent market validation. Paid-customer proof. Third-party design-partner proof. Willingness to pay. Product-market fit.

**Correct label, to be used without variation:**

> Cross-account, founder-controlled, public-repo technical proof.

**Rule.** Any material describing cross-account work — internal, investor-facing, or otherwise — must carry that label. Substituting a customer-validation label is a claim-discipline breach, not a wording preference.

---

## 7. Market Validation Deferral Rule

Market validation, real-prospect contact, outside-user validation, willingness-to-pay evidence, and paid-customer proof are **deferred commercial gates**. They are:

- **not** blockers for Gates 1 through 7;
- **not** blockers for technical beta completion;
- **not** deleted, dismissed, or treated as unnecessary;
- **not** satisfied by anything a founder-controlled account produces.

Their absence must continue to be visible in any readiness statement. Deferring a gate does not lower the bar it sets when it arrives.

## 8. Parallel Execution Grid

The lane table describes future separately authorized work packages. It does not itself authorize file writes, repository writes, implementation, publishing, merge, provider spend, deployment, billing, outreach, or use of private/customer/production data.

Lanes A–H may proceed in parallel **only** under strict lane separation: each lane touches only its own files and stops at its own boundary. Where a lane's next step is a protected gate (§9), the lane stops and waits.

| Lane | Work | Hard stop |
| --- | --- | --- |
| **A — Public Demo Cleanup** | Remove internal docs; clean README and demo objectives; fix stale test-count language; add LICENSE; add `.gitignore`; run scans and tests | Stop before publishing |
| **B — Cross-Account Repo Proof Prep** | Prepare the AKIOR or separate-account public-repo proof plan; define safe-repo criteria | Stop before any external publishing or action unless separately authorized by the founder |
| **C — Founder No-Terminal UX** | Define and, when separately authorized by the founder, build the local founder / non-developer operator journey: start, status, evidence, decision, export, without raw terminal dependence | No production deployment |
| **D — Repeatability / Crash-Test Matrix** | Prepare repeated test cases, failure cases, safe repos, and evidence criteria | Bounded to safe targets |
| **E — Beta Spine Integration Map** | Inventory PR #200 and branch-only work; identify what belongs in beta | Do not merge without founder authorization |
| **F — Investor Evidence Map** | Convert the current evidence ladder into an investor-safe proof story | Maintain claim discipline; no readiness claims |
| **G — Founder-Controlled Commercial Pilot Prep** | Draft pilot logic and the paid-proof definition | Do not send outreach without founder authorization |
| **H — SaaS Foundation** | Product brief; user roles; repo connection model; data policy; pricing hypothesis; billing design; security boundaries; hosted architecture sketch; deployment plan; optional non-production shell only | No live auth, billing, deployment, private or customer data, or production claims |

**Lane separation rule.** Parallel work is permitted because these lanes are reversible, bounded, and non-live. Any lane that discovers it must touch a live path, a secret, a spend path, or a protected file stops and escalates rather than continuing.

## 10. Claim Discipline and Label Separation

These labels are distinct and must never be collapsed into one another:

| Label | Means | Does **not** mean |
| --- | --- | --- |
| **Built** | Code exists | Tested |
| **Tested** | Named tests passed on named code | Independently checked |
| **Checker-clean** | An independent checker found no blocking defect on an exact candidate | Advisor-ready |
| **Advisor-ready** | A separate read-only advisor reviewed the same unchanged candidate | Founder-accepted |
| **Pushed** | Code reached a remote branch | Merged |
| **Merged** | Reachable on the protected path | Founder-accepted |
| **Founder-accepted** | The founder performed the accepting act at a gate | Published |
| **Publicly published** | Visible to people outside the founder | Used by anyone |
| **Customer-used** | A person outside the founder's control used it | Paid |
| **Paid** | A real payment occurred and was honestly recorded | Commercially ready |
| **Commercially ready** | Scored readiness, license/IP register, support model | Production ready |
| **Production ready** | A defined production-readiness checklist, risk review, and operating-readiness review have passed | SaaS ready |
| **SaaS ready** | Hosted mechanics proven end to end | — |

**Safe language.**

- "FounderGate has proven controlled technical workflows under defined constraints."
- "FounderGate can use founder-controlled cross-account repositories as technical evidence."
- "Market validation is deferred and is not a blocker to the current technical proof path."
- "A real payment, even from a narrow market or friend, may count as paid-customer evidence if honestly recorded."

**Forbidden language.**

- "AKIOR proves outside-customer validation."
- "FounderGate is production-ready."
- "FounderGate is commercially proven."
- "FounderGate is SaaS-ready."
- "FounderGate is secure / compliant / certified."
- "Market validation is required before cross-account technical proof."
- "Outside-user validation blocks current technical completion."

## **1. Overview**

FounderGate is a reusable software-development harness with a founder-facing control plane.

The founder is a non-developer owner. The founder should not operate terminals, write commands, manage dev servers, read code, inspect raw logs, copy prompts between tools, or supervise AI workers directly.

The founder uses a simple dashboard to:

* Open a harnessed project [V8-A1]  
* Review plain-English project status [V8-A1]  
* View-only gate cards [V8-A1]  
* View activity evidence [V8-A1]  
* Ask Project Guide what is happening (read-only explanation) [V8-A4]  
* Start, stop, restart, and refresh app previews [V8-A2]  
* Report bugs with screenshots [V8-A2]  
* Browse safe project files [V8-A3]  
* Open GitHub links [V8-B]  
* See connected services (read-only status cards) [V8-B]  
* Approve real gates [V8-B — after the Gate/Witness Engine is wired and proven]  
* Perform witnesses [V8-B+ / GATED]  
* Write simple notes [V8-B]  
* Start, pause, resume, or stop safe runs through controlled buttons [V8-B]  
* Create a new harnessed project from a safe blueprint [V8-C]  
* Open-source worker trials [V8-E]

*Maturity labels are binding: the roadmap never implies V8-A1 can do what a later stage delivers.*

The technical machine floor remains behind the dashboard:

* CTO / Terminal-0  
* Advisor lane  
* Builder workers  
* Checker workers  
* Worker cages  
* Locks  
* Evidence bus  
* Lane contracts  
* CI  
* Playwright  
* GitHub  
* Supabase / Vercel / Docker / local runtimes  
* Role prompts  
* Wide/narrow execution rules  
* Merge-sheriff workflow  
* Audit log — append-only in V8-A/V8-B; tamper-evident (hash-chain or signed checkpoints) in V8-D  
* Model/provider risk handling

### Core positioning

*FounderGate is a reusable software-development harness and founder-facing control plane. Each project is scaffolded with a .foundergate/ harness folder that stores project truth, evidence, gates, lanes, notes, integrations, locks, role prompt versions, and execution state. The FounderGate dashboard attaches to one or more harnessed projects and translates their technical state into plain-English controls, previews, evidence, and decisions for a non-developer founder. Multi-project is designed into the architecture, but execution remains single-project safe until second-project proof validates the model.*

### Brutal honesty

FounderGate should not become an overbuilt dashboard platform before the harness proves itself.

The priority is:

1. Prove the harness works.  
2. Prove the dashboard reads real repo-local harness truth.  
3. Prove the founder can operate without terminal copy-paste.  
4. Prove one project safely.  
5. Prove safe autonomous wide work.  
6. Prove sensitive work stops correctly.  
7. Prove a second project.  
8. Only then expand toward deeper platform behavior.

V8.11 avoids early overbuild:

* No full project-management platform.  
* No complex portfolio analytics.  
* No Notion clone.  
* No GitHub clone.  
* No full project clone with secrets/data.  
* No advanced snapshot/restore UI before restore is proven.  
* No global multi-project autonomous execution before second-project proof.

But V8.11 does not weaken safety:

* Project boundaries remain hard.  
* Secrets never copy by default.  
* Notes cannot become hidden worker instructions.  
* Chat cannot execute arbitrary commands.  
* GitHub is visible but not the founder-safe write surface.  
* Docker is gated.  
* Production data remains production.  
* Evidence remains disk/source-bound.  
* Sensitive live-action paths are narrow.  
* Terminal-0 remains merge sheriff.  
* Advisor remains read-only.  
* Dashboard never invents state.  
* Schema exists before UI.

## **3. UI/UX Design**

### Design goal

The UI should be simple enough that a non-developer founder can use it, but not so simplified that it hides risk.

The dashboard should feel like:

* A founder showroom  
* A safe control panel  
* A plain-English project console  
* A window into the harness  
* A calm operating room for software work

It should not feel like:

* A developer IDE  
* A GitHub clone  
* A Jira clone  
* A Notion clone  
* A cloud console clone  
* A raw terminal wrapper with prettier buttons

### Visual tone

* Calm  
* Spacious  
* Plain-English  
* Beautiful but restrained  
* Serious about danger  
* Warm and premium, not cold enterprise  
* Helpful without being cute  
* Honest when blocked or unsafe

### Accessibility / Low-Hand Mode (N7, C8)

This is a named, measured product layer, not accommodation. The founder is post-hand-surgery; this layer is core product.

Requirements:

* Large buttons (minimum 48px touch target)  
* One-action gates (never multi-step approve on one card)  
* Voice-note input for notes and bug reports  
* Read-aloud summaries of status and evidence  
* No tiny controls on gate cards  
* Keyboard-light workflows (minimal typing required)  
* Copy-paste-reduction score tracked in Bench  
* Helper handoff mode (a trusted person can assist without full control) — (Helper Handoff Mode is planned but inactive in V8-A1. V8-A1 is single local founder user only. Helper login/identity/session/audit comes later.)  
* Mobile-friendly status view  
* A "tell me what to do next" button always visible  
* Emergency pause always visible (fixed position, never in a menu)

Founder Hand-Burden score tracked in Bench:

* How many clicks to complete a gate?  
* How much typing required per session?  
* How many terminal copies still happening?  
* How many times founder needed outside help?

### 6.1 Data Classification Model (C3)

| Class | Meaning | File Cabinet behavior | Bug Collector behavior | Worker Cage behavior |

| PUBLIC_SAFE | Safe to show externally only if the founder approves. Not automatically public on the internet. | View/copy/download | Standard capture | Standard access |

### 6.2 Cost Budget Engine (C4)

The Cost Budget Engine prevents runaway compute and API costs.

**V8-A1 cost guard means schema/config, visible limits, paid-service block in UI/policy, and same-failure loop policy definition. Runtime enforcement against worker runs begins when Run Launcher / worker execution exists in V8-B. V8-A1 must not imply it can stop untracked workers.**

#### Cost controls

| Control | Purpose |
| ----- | ----- |
| Max worker runtime per run | Stop workers that run too long |
| Max retries | Stop grinding on the same failure |
| Max CI reruns | Stop burning CI on flaky tests |
| Max paid API calls | Stop unexpected API charges |
| Max storage growth | Stop evidence storage from exploding |
| Paid-service gate | Any paid service requires founder gate |
| Cost summary per run | Show founder what each run cost |
| Quota % in every checkpoint | Always visible in dashboard |
| Loop detection | Same failure 3 times = park the lane |

#### Cost guard split (C6)

*V8-A1 cost guard means schema/config, visible limits, paid-service block in UI/policy, and same-failure loop policy definition. Runtime enforcement against worker runs begins in V8-B when Run Launcher / worker execution exists. V8-A1 must not imply it can stop untracked workers. Before V8-B worker execution, the cost guard is a displayed policy/config blocker, not a runtime worker-kill system. Agents never run wide before the guard exists — and agents only run wide from V8-B. V8-B ships runtime enforcement plus the full cost dashboard with cost summary per run, quota %, and cost-per-PR/project tracking. Paid-service activation always requires a founder gate.*

#### Cost Budget Engine law (C4)

*Every run has a cost budget: max worker runtime, max retries, max CI reruns, max paid API calls, max storage growth. A paid-service gate blocks any service that costs money. Cost summary per run and quota % are shown in every checkpoint. Loop detection parks a lane after the same failure occurs three times — the lane does not grind. Agents never run wide before the cost guard exists — wide runs begin only in V8-B, where runtime enforcement is active.*

## **10. Wide vs Narrow Execution Model**

### Core principle (established historically; in force in V8.11)

FounderGate should run work as widely as possible only while the work is harmless, reversible, bounded, and non-sensitive.

FounderGate must become narrow and conservative around live-action paths, privacy-sensitive paths, irreversible actions, secrets, tokens, gates, rollback, executor, and session-token code.

Plain-English version:

*Go wide in the safe factory floor. Go narrow at the blast doors.*

### Wide Work Law

*Run autonomous wide work until the next true founder gate. Do not stop between harmless waves. Do stop before irreversible, privacy-sensitive, live-action, production-data, secret-bearing, payment, legal, deletion, public-release, or gate-changing activation.*

### Wide-safe work

Wide autonomous work is allowed for lanes that are:

* Reversible, Non-secret, Non-production  
* Non-live-action, File-bounded, Testable  
* Non-destructive, Non-privacy-sensitive  
* Covered by lane contracts

Examples:

* Docs updates, Tests, Fixtures  
* UI polish in non-sensitive files  
* Screenshot generation, Playwright tests  
* File classification, Evidence indexing  
* Notes summarization, Read-only audits  
* Non-sensitive refactors, Accessibility review  
* Mock-provider improvements

### Narrow Path Law

*For /live, /local-action, session-token, executor, rollback, gate code, production-data paths, secret-bearing paths, send/fire paths, and any live-capable action path: one primary runtime builder only, one independent checker/reviewer, and Terminal-0 as merge sheriff.*

### Narrow-sensitive work

Narrow work is mandatory for:

* /live, /local-action  
* Session tokens, Executors, Rollback  
* Gate code, Production data, Secrets  
* Email/SMS send paths, Payment paths  
* Auth/security paths, Permission systems  
* Deletion paths, Public deployment paths  
* Anything that can affect real users or real data

### Narrow-sensitive staffing

For these paths:
One primary runtime builder  
One independent checker/reviewer  
Terminal-0 as merge sheriff  
Advisor as read-only verifier if needed

Founder gate/witness where required

No swarm edits. No ten-agent live path. No duplicate writers.

### Merge Sheriff Law

*Terminal-0 is the merge sheriff. Workers may propose. Builders may write in their lane. Checkers may inspect. Advisor may verify read-only. Only Terminal-0 may merge finished work into the protected product path, and only after evidence requirements are satisfied.*

### One Writer Per Repo Law

*At any moment, each repo has one authorized writer path. Safe lanes may run wide, but write boundaries must be explicit. Sensitive/live-capable paths allow only one primary runtime builder and one independent checker.*

## **15. Exhaustion Law and UI Exhaustion Chain (B6)**

**For V8-A1, this chain uses the V8-A1 subset: spec/scope, fixture data, selftest/schema validation, minimal Playwright smoke screenshot, cannot-invent-state test, and exact-SHA CI. Full Playwright evidence viewer and hostile checker workflow are V8-B. This clarifies maturity; it does not weaken the chain.**

### The UI Exhaustion Chain — explicit ordered law

Before any UI work reaches the founder it must survive, in order:

1. Spec card approved — plain-English understanding, done meaning, will-not-do list, open questions  
2. Built on data copies — never live stores; production-data law enforced  
3. Selftests pass in-repo — code proves itself in its own repo  
4. Playwright robot-user testing — an automated real browser clicks the buttons, types in the boxes, submits the forms, capturing screenshots and recordings at every step; if the robot can't use it, the founder never sees it  
5. Hostile independent checker attacks it — tries to break, fake, or find hidden paths  
6. False-green report — honestly stating what the tests proved and did NOT prove  
7. Exact-SHA CI green on the final code — not an earlier draft  
8. Only then a plain-English card with screenshots and one button reaches the founder

### Playwright split (B3)

*V8-A includes MINIMAL Playwright smoke evidence — screenshot capture proving each V8-A screen renders and its primary action works — mandatory from the first UI build step. The full Playwright evidence system and its dashboard viewer surface arrive in V8-B. The deferral never applies to testing itself.*

### Anti-repeat law (B6)

*Every bug the founder personally catches becomes a new automated check — the system may be wrong, but never wrong the same way twice.*

### Notes-to-work path [V8-B — not V8-A1]

1. Founder writes note  
2. Project Guide summarizes intent  
3. Founder chooses "Turn into work"  
4. Structured card is created  
5. Risk and proof requirements assigned  
6. CTO accepts into queue

### Blueprint creation path [V8-C — not V8-A1]

1. Founder chooses blueprint  
2. Founder answers intake questions (data classification applied)  
3. Harness scaffold is created  
4. Secrets/live data are not copied  
5. Integrations start disconnected or test-only

7. Project appears in Projects screen

## **19. Operating Laws — V8.11 Consolidated (1–71)**

1. Founder never enters the machine floor.  
2. Plain English first.  
3. No naked localhost.  
4. No fake dashboard state.  
5. Repo-local truth first.  
6. Disk-first truth.  
7. Exact-SHA proof.  
8. No self-certification.  
9. Builder never checks its own work.  
10. Workers are workers, never decision-makers.  
11. AI is restrained by walls, not promises.  
12. Live stores are production.  
13. Inbound content is untrusted.  
14. Project Guide is not an unrestricted terminal.  
15. Raw chat becomes work only through structured lanes.  
16. Notes are memory, not executable instructions.  
17. Preview is not live.  
18. Screenshot is evidence, not proof of correctness.  
19. Founder bugs become Bench events.  
20. Founder attention is reserved for gates, witnesses, judgment, and human perception.  
21. CTO must exhaust tests/checkers/evidence before bothering founder.  
22. Project boundaries are hard boundaries.  
23. New projects are created from blueprints, not full clones.  
24. Blueprints strip secrets and live data by default.  
25. Activity is a founder-readable evidence timeline, not a replacement for GitHub.  
26. Snapshots are not backups unless restore is tested.  
27. GitHub is visible but not the founder-safe operating surface.  
28. External integrations are labeled, scoped, permissioned, and revocable.  
29. Docker is gated and sandboxed.  
30. Global actions default to viewing, pausing, and stopping — not starting or writing.  
31. Human expert escalation is mandatory for legal, IP, security incidents, payments, tax, HR, breach, health claims, and production security architecture.  
32. Advisor must operate as Solutions Architect / Technical Advisor to the non-developer founder.  
33. Terminal-0 must operate as CTO/factory manager and merge sheriff.  
34. Terminal-0 must read, compare, and write disk state throughout the workflow.  
35. Wide autonomous work continues through harmless waves until the next true founder gate.  
36. Harmless work should not interrupt the founder.  
37. Irreversible, privacy-sensitive, live-action, secret-bearing, and production actions must stop for gate/witness/expert review.  
38. Sensitive live-action paths require one primary runtime builder, one independent checker, and Terminal-0 as merge sheriff.  
39. Lane contracts are required before work begins.  
40. Role prompts are harness behavior artifacts and must be versioned, reviewed, and checked for staleness.  
41. (B2) Stranger Test: Every founder surface must pass the stranger test at every stage gate.  
42. (B5) Worker Trial Ladder: Open-source workers enter at T0/T1 and follow the mandatory 6-step ladder. No worker skips steps. Closed tools are tools, never authorities.  
43. (B6) UI Exhaustion Chain: Before any UI work reaches the founder it must survive spec card → data copies → selftests → Playwright → checker → false-green report → exact-SHA CI → then founder card. V8-A includes minimal Playwright smoke evidence; full system in V8-B. Every founder-caught bug becomes an automated check.  
44. (C2) Dashboard Hard Priority Order: The founder's 8 questions appear in strict priority order. Everything else is secondary and collapsed.  
45. (C3) Data Classification: Every file, evidence packet, screenshot, note, integration, and worker input carries a data class. V8-A: basic layer. V8-B–D: full enforcement.  
46. (C4) Cost Budget Engine: Every run has a cost budget. Loop detection parks a lane after 3x same failure. V8-A1: displayed policy/config guard only (schema/config, visible limits, paid-service block in UI/policy, loop policy definition). V8-B: runtime enforcement + full dashboard. Agents never run wide before the guard exists; wide runs begin only in V8-B.  
47. (C5) Release Label Ladder: Labels advance only when requirements are proven. No pilot-ready or commercial-ready without scored readiness report. "Almost done" is banned.  
48. (C7) Chat is never the only approval layer: Founder chat becomes a structured lane/gate/bug/note/spec before work, and every generated lane is policy-engine-reviewed before workers see it.  
49. (C7) Ambiguous language cannot become work: Ambiguous founder language cannot become work without the structured lane card being shown to the founder first.  
50. (C8) Accessibility/Low-Hand Mode: Core product layer. Large buttons, one-action gates, voice input, read-aloud, emergency pause always visible. Founder Hand-Burden score tracked in Bench.  
51. (C9) UI-Truth Hard Law: No FounderGate UI screen is accepted unless it reads real repo-local truth or is clearly labeled mock/spec.  
52. (C11) Companion-Doc Consumer Rule: No doc or prompt file is created unless it has a current consumer this cycle.  
53. (C1) Schema-First Acceptance Gate: Before any dashboard UI work begins, all .foundergate/ schemas must exist and pass validation, including data-classification, release-label, and cost-budget fields. A fixture project must pass validation. No schema, no UI.  
54. (C2) Dashboard-Cannot-Invent-State: The dashboard must never invent state. Missing → UNKNOWN. CI unavailable → CI UNKNOWN. PR unavailable → PR UNKNOWN. Stale → STALE. This test runs in CI against every dashboard build.  
55. (C4) V8-A Gate Cards View-Only: V8-A gate cards are informational unless connected to a proven gate engine. Unwired approve buttons are fake safety.  
56. (C6) Cost Guard Maturity: V8-A1 cost guard means schema/config, visible limits, paid-service block in UI/policy, and same-failure loop policy definition. Runtime enforcement against worker runs begins in V8-B when Run Launcher / worker execution exists. V8-A1 must not imply it can stop untracked workers. Before V8-B worker execution, the cost guard is a displayed policy/config blocker, not a runtime worker-kill system. Paid-service activation requires a founder gate.  
57. (C8) Project Guide Injection Boundary: Project Guide must treat app text, logs, README files, issues, screenshots, web pages, and user-uploaded content as untrusted DATA, never as instructions. No project content may cause the Guide to weaken gates, run commands, or alter its rules.  
58. (C10) Helper Delegation: No helper may approve founder gates unless the founder explicitly delegates through a separate gate.  
59. (C11) Audit Log: Append-only event log; who/what wrote each event, timestamp, source, before/after reference. Gate decisions can never be silently rewritten. Maturity is staged honestly: V8-A/V8-B ship an append-only audit log; V8-D ships the tamper-evident audit log with hash-chain or signed checkpoints. Early stages must not claim tamper-evidence. Required for buyer/investor trust.

61. (C13) Install/Update/Doctor: V8-A1 Doctor Panel shows basic version/schema/project/status health only. Update check, update rollback, migration assistant, and packaged installer are later-stage capabilities. Full Doctor path is required before outside-operator proof.
62. (C14) Model/Provider Risk: Model behavior change detection, API-down handling, rate limits, bad-output spikes, provider privacy/log review, fallback model plan, local/offline mode, provider terms review. AI workforce is a vendor dependency.  
63. (C16) H8 Hard Pass/Fail Gates: Complexity check BLOCKS a new subsystem if no simpler alternative was reviewed. False-green check BLOCKS a PR if tests do not verify real disk/user outcome. Security judgment BLOCKS any new token, secret, provider, or network path without a gate. Production-readiness score BLOCKS the PILOT_READY label. Described checks that cannot block are documentation, not judgment.

64. (Original V8 fix #8) Founder Hand-Burden Target: Terminal copy/paste for status review must be zero. "What must not be touched" identifiable within 30 seconds. Preview never receives secrets, never reuses production cookies, never controls Project Guide. Screenshots data-classified. Unknown state shows UNKNOWN. Prompt injection tested.  
66. (Original V8 fix #5) License/IP Register: Any open-source worker, copied component, or AI tool must enter the License/IP Register before real use. Unknown license/IP risk blocks commercial/pilot claims. Human legal review required for high-risk or unclear licenses. Register is concrete .foundergate/license_ip_register.json artifact.  
67. (Original V8 fix #7) Local/Offline Fallback: If AI provider is down, FounderGate degrades to read-only dashboard/status mode. Critical status readable from disk without AI. Fallback model labeled. Capability reduction shown plainly. No live action during unknown provider state. Project Guide unavailable does not make dashboard unusable.  
68. (Original V8 fix #9) Source-of-Truth Precedence: When sources of truth disagree, dashboard and advisor show CONFLICT and identify the disagreeing sources. Never silently pick the convenient answer. For repo files and project-local state, current disk/Git wins over roadmap text, docs, chat transcripts, and model memory.
